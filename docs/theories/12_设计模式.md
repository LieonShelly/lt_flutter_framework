### 设计模型的类型
- 1. 创建型模式（Creational Patterns）：解决“怎么生”的问题
    - 典型代表
        - 工厂模式（Factory / Abstract Factory）： 屏蔽复杂的创建细节，调用方只需要提需求，工厂负责生产。
        - 单例模式（Singleton）： 保证全局唯一性，常用于配置管理器、数据库连接池等需要严格控制实例数量的场景。
        - 建造者模式（Builder）： 一步步构建一个包含多个部件的复杂对象，比如组装一个定制化的 HTTP Request。
    - 架构师视角： 当你发现系统里的对象初始化过程极其繁琐，或者需要根据不同业务上下文动态决定创建哪种具体实现时，这就到了创建型模式出场的时候了。

- 2. 结构型模式（Structural Patterns）：解决“怎么组装”的问题
    - 这类模式关注如何将类或对象组合成更大的结构，就像搭积木一样，让原本独立甚至接口不兼容的类能够协同工作。
    - 典型代表：
        - 代理模式（Proxy）： 找个替身来控制对原对象的访问，这是 Spring AOP 实现无侵入式切面编程的核心底层逻辑。
        - 装饰器模式（Decorator）： 不改变原类结构，动态地给对象套上一层层新功能（比如 Java 的 IO 流设计 new BufferedReader(new InputStreamReader(...))）。
        - 适配器模式（Adapter）： 解决接口不兼容的问题，让原本水火不容的类能一起工作，属于经典的遗留系统整合“打补丁”利器。
    - 架构师视角： 在系统演进、引入第三方依赖或重构遗留系统时，结构型模式是我们的救星。它能帮助我们在不修改原有核心代码（遵循开闭原则）的前提下，平滑地扩展或整合新结构。

- 3. 行为型模式（Behavioral Patterns）：解决“怎么沟通”的问题
    - 这类模式不仅关注类和对象本身，更关注它们之间的通信机制和职责分配。它决定了系统在运行时，业务逻辑和控制流是如何流转的。
    - 典型代表：
        - 策略模式（Strategy）： 封装不同的算法或业务规则，允许在运行时相互替换，是干掉代码里成百上千行 if-else 或 switch-case 的首选。
        - 观察者模式（Observer）： 实现一对多的订阅与分发解耦，事件驱动架构（EDA）和 MQ 消息队列的底层思想皆源于此。
        - 责任链模式（Chain of Responsibility）： 像流水线一样依次处理请求，非常适合做 API 网关的鉴权、限流、日志过滤等拦截器链。
    - 架构师视角： 这是日常业务开发中最常用的一类。如果你的核心业务流程经常因产品需求变更而修改，或者需要高度解耦各个独立的业务节点，行为型模式能让代码具备极强的弹性和可测试性。


## 创建型模式（Creational Patterns）- 共 5 种
- 这类模式的共同目标是：优雅地创建对象，隔离对象的创建和使用过程。
- 单例模式 (Singleton)：全局唯一。确保一个类只有一个实例，并提供一个全局访问点（如：全局配置管理器、连接池）。
- 工厂方法模式 (Factory Method)：延迟到子类实例化。定义一个创建对象的接口，但让实现这个接口的类来决定实例化哪个类。
- 抽象工厂模式 (Abstract Factory)：产品族创世神。提供一个接口，用于创建相关或依赖对象的家族，而不需要明确指定具体类（如：跨平台UI组件库生成）。
- 建造者模式 (Builder)：流水线组装。将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示（如：链式调用的 StringBuilder）。
- 原型模式 (Prototype)：克隆分身。通过拷贝现有的实例来创建新对象，而不是每次都去繁琐地 new（如：复杂对象的快速深/浅拷贝）。

## 二、 结构型模式（Structural Patterns）- 共 7 种
- 这类模式的共同目标是：处理类或对象的组合，解决不同实体之间如何协同工作的问题。

- 适配器模式 (Adapter)：接口转换器。将一个类的接口转换成客户希望的另外一个接口，解决新老系统接口不兼容的痛点。

- 装饰器模式 (Decorator)：动态套娃。在不改变原有对象结构的前提下，动态地给该对象增加一些额外的职责（如：给原有的业务组件一层层套上日志、性能监控功能）。

- 代理模式 (Proxy)：业务替身。为其他对象提供一种代理以控制对这个对象的访问（如：RPC远程调用、Spring AOP切面）。

- 外观模式 (Facade)：统一迎宾台。为子系统中的一组接口提供一个一致的界面，屏蔽内部复杂性（如：提供一个统一的 API 网关聚合底层微服务接口）。

- 桥接模式 (Bridge)：抽象与实现解耦。将抽象部分与它的实现部分分离，使它们都可以独立地变化（如：多维度变化的系统，如“不同颜色的”、“不同形状的”画笔）。

- 组合模式 (Composite)：树形结构。将对象组合成树形结构以表示“部分-整体”的层次结构，使得客户端对单个对象和复合对象的使用具有一致性（如：公司组织架构树、文件系统目录）。

- 享元模式 (Flyweight)：资源共享。运用共享技术有效地支持大量细粒度的对象，极大地减少内存开销（如：Java中的 String 常量池、线程池）。

## 三、 行为型模式（Behavioral Patterns）- 共 11 种
- 这类模式的共同目标是：描述类或对象怎样交互以及怎样分配职责。

- 策略模式 (Strategy)：算法替换。定义一系列算法，把它们一个个封装起来，并且使它们可相互替换，消灭冗长的 if-else。

- 观察者模式 (Observer)：发布-订阅。定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并被自动更新（如：消息队列的底层思想）。

- 责任链模式 (Chain of Responsibility)：击鼓传花。为解除请求的发送者和接收者之间耦合，而使多个对象都有机会处理这个请求（如：Web 过滤器的拦截链、审批流）。

- 模板方法模式 (Template Method)：算法骨架。定义一个操作中的算法骨架，而将一些步骤延迟到子类中，实现代码复用。

- 状态模式 (State)：状态驱动。允许对象在内部状态改变时改变它的行为，对象看起来好像修改了它的类（如：电商订单状态机流转）。

- 命令模式 (Command)：请求封装。将一个请求封装为一个对象，从而使你可用不同的请求对客户进行参数化（如：实现撤销、重做、排队任务）。

- 迭代器模式 (Iterator)：安全遍历。提供一种方法顺序访问一个聚合对象中各个元素，而又不需暴露该对象的内部表示。

- 中介者模式 (Mediator)：网状变星状。用一个中介对象来封装一系列的对象交互，使各对象不需要显式地相互引用，从而使其耦合松散（如：复杂的聊天室系统、MVC中的 Controller）。

- 备忘录模式 (Memento)：状态快照。在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态，用于随时恢复（回滚操作）。

- 访问者模式 (Visitor)：外部扩展。表示一个作用于某对象结构中的各元素的操作，它使你可以在不改变各元素的类的前提下定义作用于这些元素的新操作（较复杂，常用于编译器或 AST 抽象语法树解析）。

- 解释器模式 (Interpreter)：自定义规则引擎。给定一个语言，定义它的文法表示，并定义一个解释器来处理这个文法（如：正则表达式解析器、SQL解析器）。
