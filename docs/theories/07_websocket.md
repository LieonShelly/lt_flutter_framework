# WebSocket 高可用架构与面试实战指南

本指南旨在提炼 WebSocket 在移动端（Flutter）开发中的核心亮点，并针对面试中的高频深挖点提供体系化的防御逻辑与话术准备。

---

## 一、 简历技术亮点打磨 (Resume Highlights)

根据项目侧重点的不同，可以从以下三个维度进行针对性描述：

### 维度一：状态管理与智能重连 (通用性最强)
> **描述建议**：设计并实现高可用 WebSocket 状态机。结合 Flutter `AppLifecycleState` 与网络连通性监听，实现前后台切换的连接自动挂起与恢复；采用 **指数退避算法 (Exponential Backoff)** 设计断线重连机制，有效避免服务端雪崩效应；实现基于双向 Ping-Pong 的心跳保活策略，提升弱网环境下的连接稳定性。

### 维度二：中心化分发总线 (架构设计感)
> **描述建议**：构建中心化长链接分发总线。在 Domain 层封装统一的 WebSocket Client，通过 **主题订阅 (Topic Subscription)** 机制按需分发实时行情、盘口深度与私有资产数据；设计数据解析隔离层，针对高频推送采用增量更新策略，大幅降低 JSON 序列化的 CPU 开销。

### 维度三：高频并发防拥堵 (资深/高阶打法)
> **描述建议**：实现极端行情下的长链接背压与防抖。针对高频并发推送场景（如行情剧烈波动），在数据接收层引入节流 (Throttling) 与消息合并队列 (Message Batching)；将高频数据的反序列化剥离至独立的 **Isolate 线程** 执行，确保 UI 主线程在极端推送压力下依然保持 60FPS 满帧运行。

## 二、 核心技术标准落地

### 1. 架构设计：全局长链接总线
*   **实现基础**：基于 `StreamController.broadcast` 构建。
*   **状态驱动**：结合 `connectivity_plus` 实现状态机驱动，支持“切后台断开、切前台恢复、网络恢复极速重连”的闭环逻辑。

### 2. 重连机制：指数退避与抖动 (Jitter)
*   **核心算法**：`Delay = min(maxDelay, baseDelay * 2^retryCount)`。
*   **抖动引入**：加入随机毫秒级 Jitter，防止海量客户端在同一秒向服务端发起重连请求（防范惊群效应）。

### 3. 数据层优化：隔离与计算分离
*   **订阅隔离**：通过 Topic 机制隔离行情、订单、资产数据流，互不干扰。
*   **性能保障**：JSON 反序列化逻辑剥离至独立 Isolate 线程池，避免主线程出现微小掉帧。

## 三、 面试官“防御指南” (面试深挖应对)

> [!CAUTION]
> 简历上写了以上词汇，面试官必定会深挖细节。以下参数和逻辑必须内化为“亲手编写”的肌肉记忆：

### 1. 心跳 (Ping-Pong) 是如何设计的？间隔是多少？
*   **标准话术**：
    > “我们前端维护一个 Timer。每隔 **10 秒** 向服务端发送一个 `{"ping": timestamp}`。如果服务端在 **3 秒** 内没有回复 `pong`，或者连续两次没收到回复，我们就认为链路已死，主动调用 `socket.close()` 并触发重连逻辑。”

### 2. 前后台切换 (AppLifecycleState) 是如何处理的？
*   **标准话术**：
    > “当应用退到后台 (`paused`) 时，为节省电量和流量，我们会延迟 **5 秒** 后主动断开 WebSocket。当应用回到前台 (`resumed`) 时，立刻触发重连，并同步调用一次 HTTP 接口拉取最新快照数据 (**Snapshot**)，确保数据一致性，之后再依赖 WebSocket 接收增量更新。”

### 3. 指数退避的具体参数是如何配置的？
*   **标准话术**：
    > “基础重试延迟（baseDelay）设为 **1 秒**。重试间隔随次数指数增长，最大延迟（maxDelay）封顶在 **30 秒**。每次重连都会加上随机抖动值。最大重试次数原则上不设上限，直到网络连接恢复。”
