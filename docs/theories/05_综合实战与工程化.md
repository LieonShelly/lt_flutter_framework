# 综合实战与工程化 (Engineering & Best Practices)
- 自动化测试：Unit Test、Widget Test、Integration Test 三者的覆盖侧重点是什么？
    -  Unit Test（单元测试）
        - 侧重点：验证单一的代码块（函数、方法或类）的纯逻辑是否正确。
        - 测试对象：数据模型（Models）、状态管理逻辑（如 Redux Reducers、Bloc、ViewModel）、工具类函数（Utils）、算法等。
        - 核心特征：
        - 极度隔离：不涉及 UI 渲染，不依赖真实的外部环境（网络、数据库），外部依赖通常会被模拟（Mock）。
        - 执行速度极快：通常在毫秒级，可以在每次保存代码时运行。
        - 高覆盖率：占据测试金字塔的底层，数量最多。
        - 典型场景：
            - 输入密码“123”，验证 isValidPassword() 函数是否返回 false。
            - 调用 fetchUserData() 后，验证 JSON 数据是否被正确解析成了 UserModel 对象。

    - Widget Test / Component Test（组件测试）
        - 侧重点：验证单一 UI 组件的渲染、布局以及用户交互逻辑。
        - 注：“Widget Test”是 Flutter 的专有名词，在 React/Vue 中称为组件测试（Component Test），在原生 iOS/Android 中通常归类为轻量级的 UI 测试。
        - 测试对象：单个按钮、复杂的列表项（ListTile）、自定义的弹窗、或者一个独立的页面（不涉及页面跳转）。
        - 核心特征：
            - 环境模拟：不需要启动完整的应用程序，而是在一个虚拟的、无头的（Headless）环境中渲染 UI 组件。
            - 关注交互与状态：主要测试“用户的操作（如点击、滑动）是否引起了预期的 UI 变化”。
            - 执行速度适中：比单元测试慢（因为涉及渲染树构建），但远快于集成测试。
            - 典型场景：
                - 向 CustomButton 传入 isLoading: true，验证界面上是否渲染了加载小菊花，且文字被隐藏。
                - 模拟用户点击“提交”按钮，验证是否正确调用了传入的 onPressed 回调函数。

    - Integration Test（集成测试）
        - 侧重点：验证多个模块组合在一起时，甚至是整个应用的端到端（End-to-End, E2E）工作流是否正常。
        - 测试对象：完整的业务流程（如登录流程、购物车结算流程）。
        - 核心特征：
        - 真实环境：必须在真实的设备（真机）或模拟器（Emulator/Simulator）上运行。它会像真实用户一样启动完整的 App。
        - 覆盖链路长：包括 UI 渲染、页面路由跳转、甚至是真实的（或部分 Mock 的）网络请求和本地数据库读写。
        - 执行速度最慢、维护成本最高：占据测试金字塔的顶端，因为一旦 UI 发生微小变动或网络延迟，测试就容易失败（即“脆弱的测试”）。
        - 典型场景：
        - 主链路验证：启动 App -> 在输入框输入账号密码 -> 点击登录按钮 -> 等待网络请求返回 -> 验证是否成功跳转到了首页（Home Screen） -> 验证首页是否展示了用户的真实昵称。
