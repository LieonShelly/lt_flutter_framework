# 综合实战与工程化 (Engineering & Best Practices)
- 自动化测试：Unit Test、Widget Test、Integration Test 三者的覆盖侧重点是什么？
    -  Unit Test（单元测试）
        - 侧重点：验证单一的代码块（函数、方法或类）的纯逻辑是否正确。
        - 测试对象：数据模型（Models）、状态管理逻辑（如 Redux Reducers、Bloc、ViewModel）、工具类函数（Utils）、算法等。
        - 核心特征：
        - 极度隔离：不涉及 UI 渲染，不依赖真实的外部环境（网络、数据库），外部依赖通常会被模拟（Mock）。
        - 执行速度极快：通常在毫秒级，可以在每次保存代码时运行。
        - 高覆盖率：占据测试金字塔的底层，数量最多。
        - 典型场景：
            - 输入密码“123”，验证 isValidPassword() 函数是否返回 false。
            - 调用 fetchUserData() 后，验证 JSON 数据是否被正确解析成了 UserModel 对象。

    - Widget Test / Component Test（组件测试）
        - 侧重点：验证单一 UI 组件的渲染、布局以及用户交互逻辑。
        - 注：“Widget Test”是 Flutter 的专有名词，在 React/Vue 中称为组件测试（Component Test），在原生 iOS/Android 中通常归类为轻量级的 UI 测试。
        - 测试对象：单个按钮、复杂的列表项（ListTile）、自定义的弹窗、或者一个独立的页面（不涉及页面跳转）。
        - 核心特征：
            - 环境模拟：不需要启动完整的应用程序，而是在一个虚拟的、无头的（Headless）环境中渲染 UI 组件。
            - 关注交互与状态：主要测试“用户的操作（如点击、滑动）是否引起了预期的 UI 变化”。
            - 执行速度适中：比单元测试慢（因为涉及渲染树构建），但远快于集成测试。
            - 典型场景：
                - 向 CustomButton 传入 isLoading: true，验证界面上是否渲染了加载小菊花，且文字被隐藏。
                - 模拟用户点击“提交”按钮，验证是否正确调用了传入的 onPressed 回调函数。

    - Integration Test（集成测试）
        - 侧重点：验证多个模块组合在一起时，甚至是整个应用的端到端（End-to-End, E2E）工作流是否正常。
        - 测试对象：完整的业务流程（如登录流程、购物车结算流程）。
        - 核心特征：
        - 真实环境：必须在真实的设备（真机）或模拟器（Emulator/Simulator）上运行。它会像真实用户一样启动完整的 App。
        - 覆盖链路长：包括 UI 渲染、页面路由跳转、甚至是真实的（或部分 Mock 的）网络请求和本地数据库读写。
        - 执行速度最慢、维护成本最高：占据测试金字塔的顶端，因为一旦 UI 发生微小变动或网络延迟，测试就容易失败（即“脆弱的测试”）。
        - 典型场景：
        - 主链路验证：启动 App -> 在输入框输入账号密码 -> 点击登录按钮 -> 等待网络请求返回 -> 验证是否成功跳转到了首页（Home Screen） -> 验证首页是否展示了用户的真实昵称。

- CI/CD 集成：如何利用 GitHub Actions 实现 Flutter 的自动化构建与分发？
    - 1. 准备工作：提取并转码签名文件
        - GitHub Actions 无法直接读取你的本地 Keychain，因此我们需要将签名文件转换为 Base64 字符串存入 GitHub Secrets。
        - 导出证书：从 Keychain 导出 Apple Distribution 证书为 Certificates.p12（记得设置密码）。
        - 下载描述文件：从 Apple Developer 网站下载对应的 profile.mobileprovision。
        - 转换为 Base64：在终端执行以下命令，将生成的一大段字符串分别复制备用。
        ```bash
            base64 -i Certificates.p12 | pbcopy
            base64 -i profile.mobileprovision | pbcopy
        ```
        - 准备 ExportOptions.plist：在 Flutter 项目的 ios/ 目录下准备一个 ExportOptions.plist 文件（指定 method 为 app-store，以及对应的 provisioningProfiles 键值对）。

    - 2. 配置 GitHub Secrets
        - 进入你的 GitHub 仓库 -> Settings -> Secrets and variables -> Actions，添加以下机密变量：
            - BUILD_CERTIFICATE_BASE64：上面生成的 .p12 Base64 字符串。
            - P12_PASSWORD：导出 .p12 时设置的密码。
            - BUILD_PROVISION_PROFILE_BASE64：上面生成的描述文件 Base64 字符串。
            - KEYCHAIN_PASSWORD：随便设置一个密码（用于在 Action 运行时创建临时钥匙串）。
            - APPSTORE_ISSUER_ID：App Store Connect API 的 Issuer ID。
            - APPSTORE_API_KEY_ID：App Store Connect API 的 Key ID。
            - APPSTORE_API_PRIVATE_KEY：App Store Connect 下载的 .p8 秘钥内容。

    - 3. 编写 GitHub Actions 工作流
        - 在项目根目录创建文件 .github/workflows/ios_deploy.yml。以下是核心的 YAML 配置模板：
        ```yaml
        name: iOS CD - Build and Distribute to TestFlight

        # 触发条件：当你打上 'v' 开头的 tag 时触发（如 v1.0.0）
        on:
        push:
            tags:
            - 'v*'

        jobs:
        build-and-deploy-ios:
            # 必须使用 macOS 运行环境
            runs-on: macos-latest

            steps:
            - name: 📦 Checkout code
                uses: actions/checkout@v4

            - name: 🍎 Install Apple Certificate and Provisioning Profile
                env:
                BUILD_CERTIFICATE_BASE64: ${{ secrets.BUILD_CERTIFICATE_BASE64 }}
                P12_PASSWORD: ${{ secrets.P12_PASSWORD }}
                BUILD_PROVISION_PROFILE_BASE64: ${{ secrets.BUILD_PROVISION_PROFILE_BASE64 }}
                KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}
                run: |
                # 创建临时变量存放证书和描述文件路径
                CERTIFICATE_PATH=$RUNNER_TEMP/build_certificate.p12
                PP_PATH=$RUNNER_TEMP/build_pp.mobileprovision
                KEYCHAIN_PATH=$RUNNER_TEMP/app-signing.keychain-db

                # 从 Base64 还原文件
                echo -n "$BUILD_CERTIFICATE_BASE64" | base64 --decode -o $CERTIFICATE_PATH
                echo -n "$BUILD_PROVISION_PROFILE_BASE64" | base64 --decode -o $PP_PATH

                # 创建临时钥匙串
                security create-keychain -p "$KEYCHAIN_PASSWORD" $KEYCHAIN_PATH
                security set-keychain-settings -lut 21600 $KEYCHAIN_PATH
                security unlock-keychain -p "$KEYCHAIN_PASSWORD" $KEYCHAIN_PATH

                # 导入证书到钥匙串
                security import $CERTIFICATE_PATH -P "$P12_PASSWORD" -A -t cert -f pkcs12 -k $KEYCHAIN_PATH
                security list-keychain -d user -s $KEYCHAIN_PATH

                # 安装描述文件 (移动到特定目录下供 Xcode 读取)
                mkdir -p ~/Library/MobileDevice/Provisioning\ Profiles
                cp $PP_PATH ~/Library/MobileDevice/Provisioning\ Profiles

            - name: 🐦 Setup Flutter
                uses: subosito/flutter-action@v2
                with:
                channel: 'stable'
                cache: true

            - name: 📦 Install Dependencies
                run: flutter pub get

            - name: 🔨 Build iOS IPA
                # 使用 --export-options-plist 告诉 xcodebuild 如何进行签名和导出
                run: flutter build ipa --release --export-options-plist=ios/ExportOptions.plist

            - name: 🚀 Upload to TestFlight
                # 使用第三方高质量 Action 调用 App Store Connect API 上传
                uses: apple-actions/upload-testflight-build@v1
                with:
                # Flutter 构建的 ipa 默认路径
                app-path: build/ios/ipa/Runner.ipa
                issuer-id: ${{ secrets.APPSTORE_ISSUER_ID }}
                api-key-id: ${{ secrets.APPSTORE_API_KEY_ID }}
                api-private-key: ${{ secrets.APPSTORE_API_PRIVATE_KEY }}

            - name: 🧹 Clean up keychain and provisioning profile
                if: ${{ always() }}
                run: |
                    # 清理机密文件，防止泄露
                    security delete-keychain $RUNNER_TEMP/app-signing.keychain-db
                    rm ~/Library/MobileDevice/Provisioning\ Profiles/build_pp.mobileprovision
        ```

- 国际化与本地化：如何处理动态语言切换及 RTL（从右向左阅读）布局适配？
    - 核心基础：基于 .arb 文件的官方方案
        - 现代 Flutter 国际化的标准做法是使用 flutter_localizations 和 .arb (Application Resource Bundle) 文件。这种方式会在编译时自动生成强类型的 Dart 类（通常是 AppLocalizations），让你在代码中通过 AppLocalizations.of(context)!.helloWorld 来安全地调用词条。
    - 二、 如何实现“无缝”的动态语言切换？
        - 在应用内提供一个按钮，点击后立即切换全站语言且不重启应用，核心在于使用状态管理来驱动 MaterialApp 的 locale 属性重建。
        - 无论你使用的是什么状态管理工具，基本架构模式如下：
            - 1. 创建一个全局的语言状态控制器
                - 我们需要一个能够持久化保存用户选择（如使用 shared_preferences），并在改变时通知 UI 的类。
            ```Dart
            import 'package:flutter/material.dart';

            class LocaleProvider extends ChangeNotifier {
                Locale? _locale;

                Locale? get locale => _locale;

                void setLocale(Locale locale) {
                    if (!L10n.all.contains(locale)) return; // L10n.all 是你在 arb 中配置的支持列表
                    _locale = locale;
                    notifyListeners();
                    // TODO: 将选择持久化保存到本地存储
                }

                void clearLocale() {
                    _locale = null; // 设为 null 将跟随系统语言
                    notifyListeners();
                }
            }
            ```
    - 2. 将状态注入到 MaterialApp
        - 在顶层挂载你的状态，并将 locale 传递给 MaterialApp。当 LocaleProvider 发出通知时，MaterialApp 会带上新的 locale 重建整个应用的 Widget 树。
        ```Dart
        // 假设使用 Provider 作为状态管理
        Consumer<LocaleProvider>(
            builder: (context, provider, child) {
                return MaterialApp(
                title: 'Global App',
                // 1. 挂载当前选中的 Locale
                locale: provider.locale, 
                // 2. 声明支持的语言列表
                supportedLocales: AppLocalizations.supportedLocales,
                // 3. 挂载本地化代理
                localizationsDelegates: AppLocalizations.localizationsDelegates, 
                home: const HomePage(),
                );
            }
        )
        ```
    - 三、 攻克 RTL (从右向左) 布局适配
        - Flutter 的 UI 系统默认就对 RTL 有着极好的支持。当 MaterialApp 的 locale 被切换为 RTL 语言（如 ar）时，框架内部的 Directionality 环境变量会自动翻转。
        - 为了让你的 UI 完美适配，你需要遵守以下几个“戒律”：
        - 1. 彻底抛弃 Left / Right，拥抱 Start / End
            - 这是最重要的思想转变。就像 iOS 原生的 leading/trailing，在 Flutter 中，涉及到方向、边距、对齐的属性，全部改用带有 Directional 后缀的类。
            - 内边距 / 外边距：
                - ❌ EdgeInsets.only(left: 16)
                - ✅ EdgeInsetsDirectional.only(start: 16)
            - 对齐方式：
                - ❌ Alignment.topLeft
                - ✅ AlignmentDirectional.topStart
            - 绝对定位：
                - ❌ Positioned(left: 10, ...)
                - ✅ Positioned.directional(textDirection: Directionality.of(context), start: 10, ...)
            - 圆角裁剪：
                - ❌ BorderRadius.only(topLeft: Radius.circular(8))
                - ✅ BorderRadiusDirectional.only(topStart: Radius.circular(8))
            - 当你使用 Directional 类时，当语言切换为阿拉伯语时，start 会自动从屏幕左侧变为屏幕右侧，无需你写任何 if-else。

        - 2. 处理具有方向性的图标
            - 像返回箭头（←）这种图标，在 RTL 模式下应该翻转变成（→）。Flutter 的 Icon Widget 提供了一个极其方便的属性：
            ```Dart
                Icon(
                    Icons.arrow_back,
                    matchTextDirection: true, // 开启后，在 RTL 环境下图标会自动水平镜像翻转
                )
            ```
            - 注意：并非所有图标都需要翻转（例如时钟、对勾 ✔️ 通常不需要），只有涉及“方向指示”的才需要开启此属性。

        - 3. 处理复杂的自定义绘图与动画
            - 如果你在应用中使用 CustomPaint 画了一些高度自定义的不对称图形，或者包含平移动画，你需要手动读取当前环境的方向来决定渲染逻辑：
            ```Dart
                final isRTL = Directionality.of(context) == TextDirection.rtl;
            ```
            - 使用 RiverPod 做状态管理
        ```Dart

            }

        ```

- 多渠道打包：如何通过 flutter build --flavor 管理不同的生产与测试环境。
    - 第一步：在 Dart 代码中区分入口
        - 为了让不同环境加载不同的基础配置（如 API Base URL），我们通常会创建多个主入口文件。
        - 定义环境配置类：
        ```Dart
        // lib/config/env.dart
        enum EnvType { dev, prod }

        class EnvConfig {
            final EnvType type;
            final String apiBaseUrl;

            EnvConfig({required this.type, required this.apiBaseUrl});

            // 全局单例
            static late EnvConfig instance;
        }
        ```
    - 创建不同的 main.dart：
        ```Dart
        // lib/main_dev.dart
        import 'package:flutter/material.dart';
        import 'config/env.dart';
        import 'app.dart'; // 你的主应用 Widget

        void main() {
            EnvConfig.instance = EnvConfig(
                type: EnvType.dev,
                apiBaseUrl: 'https://api-dev.yourdomain.com',
            );
            runApp(const MyApp());
        }
        // lib/main_prod.dart
        // ... 同理，配置 prod 的 URL
        ```

    - 第二步：配置 iOS 端 (Schemes & Build Configurations)
        - 这是 Flutter 联调原生最关键的一步。当你在终端运行 flutter build ipa --flavor dev 时，Flutter 的底层逻辑是：去 iOS 工程里寻找名为 dev 的 Scheme，并使用名为 Release-dev 的 Build Configuration 进行打包。
        - 创建 Build Configurations：
            - 打开 ios/Runner.xcworkspace。
            - 点击左侧导航栏的顶层 Runner Project -> Info 标签页 -> 找到 Configurations。
            - 点击 + 号，分别复制原有的 Debug、Release、Profile，并加上对应的后缀。
            - 最终你应该有这几个配置项：Debug-dev, Release-dev, Profile-dev，以及 Debug-prod, Release-prod, Profile-prod。
            - 创建 Schemes：
                - 在 Xcode 顶部选择 Scheme 列表 -> Manage Schemes。
                - 点击 + 号，新建名为 dev 的 Scheme，并将 Target 选为 Runner。再新建一个名为 prod 的 Scheme。
                - 选中 dev Scheme -> 点击 Edit -> 将 Run、Test、Profile、Archive 等步骤的 Build Configuration 分别映射到对应的 -dev 版本（例如 Archive 对应 Release-dev）。
                - 对 prod Scheme 执行相同操作。
                - 设置不同的 Bundle ID 和 App Name (可选)：
                - 进入 Runner Target -> Build Settings -> 搜索 Product Bundle Identifier。
                - 展开它，你会看到刚才创建的所有 Configuration。你可以给 Debug-dev 和 Release-dev 设置为 com.yourcompany.app.dev，给 prod 设置为 com.yourcompany.app。
                - 同理，可以在 Info.plist 中使用 User-Defined 变量来动态改变 App Display Name。

        - 第三步：配置 Android 端 (build.gradle)
            - Android 的配置相对简单，因为 Gradle 原生支持 Flavor 组合。
            - 打开 android/app/build.gradle，在 android { ... } 块中添加：

            ```Gradle
                android {
                    // ...
                    
                    // 1. 定义维度
                    flavorDimensions "environment"

                    // 2. 配置具体的 productFlavors
                    productFlavors {
                        dev {
                            dimension "environment"
                            applicationIdSuffix ".dev" // 会在原 applicationId 后面自动追加
                            versionNameSuffix "-dev"
                            resValue "string", "app_name", "App (Dev)"
                        }
                        prod {
                            dimension "environment"
                            // prod 保持默认 applicationId 不变
                            resValue "string", "app_name", "App"
                        }
                    }
                }
            ```
    - 第四步：在终端构建与运行
        - 配置完毕后，你就可以通过组合 --flavor 和 -t (target) 参数来随意切换环境了。
        - 运行到模拟器/真机进行测试：
        ```shell
            # 运行测试环境
            flutter run --flavor dev -t lib/main_dev.dart

            # 运行生产环境
            flutter run --flavor prod -t lib/main_prod.dart
            打包 iOS 生产包 (IPA)：

            Bash
            flutter build ipa --flavor prod -t lib/main_prod.dart --export-options-plist=ios/ExportOptions.plist
        ```

- 分层路由设计：如何在大型应用中设计解耦的路由系统（如使用 GoRouter）。
    - 一、 路由表的分治与模块化 (Route Modularization)
        - 不要在顶层声明所有路由，而是让每个业务模块（例如 Auth、Wallet、Swap）自己管理和暴露属于自己的路由表。
        - 1. 定义模块路由接口：
        - 每个模块对外提供一个静态的 List<RouteBase> 数组。
            ```Dart
            // wallet_routes.dart (钱包模块内部)
            class WalletRoutes {
                static const String root = '/wallet';
                static const String transfer = 'transfer'; // 子路由不要加 '/'
                static const String history = 'history';

                static final List<RouteBase> routes = [
                    GoRoute(
                    path: root,
                    builder: (context, state) => const WalletHomeScreen(),
                    routes: [
                        // 嵌套子路由，享受 GoRouter 的栈管理
                        GoRoute(
                        path: transfer,
                        builder: (context, state) {
                            // 通过 state.extra 传递复杂参数 (强类型化)
                            final args = state.extra as TransferArgs?; 
                            return TransferScreen(args: args);
                        },
                        ),
                        GoRoute(
                        path: history,
                        builder: (context, state) => const HistoryScreen(),
                        ),
                    ],
                    ),
                ];
            }
            ```
        - 2. 顶层组装 (AppRouter)：
            - 主工程的 Router 配置只负责“拼图”，完全不需要关心各个模块内部的页面结构。
            ```Dart         
                // app_router.dart (主工程)
                final appRouter = GoRouter(
                    initialLocation: WalletRoutes.root,
                    routes: [
                        ...AuthRoutes.routes,
                        ...WalletRoutes.routes,
                        ...SwapRoutes.routes,
                        ...NftRoutes.routes,
                    ],
                );
            ```
    - 二、 引入抽象层：剥离对 context.go 的强依赖
        - 如果你的 UI 组件里到处都是 context.go('/wallet/transfer')，这就意味着你的 UI 组件与特定的 URL 路径以及 GoRouter 这个第三方库强耦合了。
        - 最佳实践是引入一个类似 iOS Coordinator 的导航抽象层。

        ```Dart
        // app_coordinator.dart
        abstract class AppCoordinator {
            void goToTransfer(BuildContext context, TransferArgs args);
            void pop(BuildContext context);
            }

            class GoRouterCoordinator implements AppCoordinator {
            @override
            void goToTransfer(BuildContext context, TransferArgs args) {
                // 只有 Coordinator 知道具体的路径结构和 GoRouter API
                context.go('${WalletRoutes.root}/${WalletRoutes.transfer}', extra: args);
            }

            @override
            void pop(BuildContext context) {
                if (context.canPop()) {
                context.pop();
                }
            }
        }
        ```
        - 通过这种方式，UI 层只需调用 coordinator.goToTransfer()，就算未来更换了路由框架，UI 层的代码也不用改动哪怕一行。

    - 三、 复杂底座：使用 StatefulShellRoute 处理 Tab 切换
        - 大多数大型应用都有底部导航栏（BottomNavigationBar）。原生的 Navigator 很难处理“切换 Tab 时保持各自页面的滚动状态和路由栈”。GoRouter 提供了 StatefulShellRoute 专门解决这个问题，这也是分层路由的核心场景。

        ```Dart
        // 组装带状态的 Tab 路由
        final tabRoute = StatefulShellRoute.indexedStack(
            builder: (context, state, navigationShell) {
                // 这是一个包含 BottomNavigationBar 的骨架屏 Widget
                return MainTabScaffold(navigationShell: navigationShell); 
            },
            branches: [
                // 分支 1: 钱包 (接入 Wallet 模块的路由)
                StatefulShellBranch(routes: WalletRoutes.routes),
                // 分支 2: Swap (接入 Swap 模块的路由)
                StatefulShellBranch(routes: SwapRoutes.routes),
            ],
        )
        ```
    - 四、 统一的守卫与拦截 (Guards & Redirection)
        - 无论是结合 Riverpod 还是 Bloc，大型应用都需要在路由层进行权限拦截（比如：未登录用户不能进入资产页，网络未连接时不能发起 Swap）。
        - 利用 GoRouter 的 redirect 功能，并在顶层结合状态管理进行驱动：
        ```Dart
        // 以 Riverpod 为例的顶层路由配置
        final routerProvider = Provider<GoRouter>((ref) {
        // 监听全局的鉴权状态
        final authState = ref.watch(authNotifierProvider);

        return GoRouter(
            initialLocation: '/home',
            // 当 authState 发生变化时，GoRouter 会自动重新计算重定向逻辑
            refreshListenable: GoRouterRefreshStream(ref.read(authNotifierProvider.notifier).stream),
            redirect: (context, state) {
            final isGoingToLogin = state.matchedLocation == '/login';
            final isLoggedIn = authState.isAuthenticated;

            // 拦截逻辑：未登录且不在登录页 -> 强制去登录
            if (!isLoggedIn && !isGoingToLogin) {
                return '/login';
            }
            
            // 已登录但还在登录页 -> 强制回主页
            if (isLoggedIn && isGoingToLogin) {
                return '/wallet';
            }

            // 返回 null 表示放行
            return null; 
            },
            routes: [ /* 模块化路由 */ ],
        );
        });
        ```

- 崩溃监控：如何捕获并上报 Dart 侧异常和 Native 侧 Crash（如 Sentry, Firebase Crashlytics）。
    - 1. Dart 侧异常：多层次拦截
    - Dart 侧的错误不会直接导致 App 闪退（通常表现为 UI 灰屏或逻辑中断），我们需要在三个层面进行拦截：
    - UI 渲染异常 (FlutterError.onError)：
    - 专门捕获 Flutter 框架在构建、布局、绘制过程中抛出的异常。

        ```Dart
        FlutterError.onError = (details) {
            // 上报给 Sentry 或 Firebase
            Sentry.captureException(details.exception, stackTrace: details.stack);
            // 生产环境下可以重写 ErrorWidget，展示一个友好的错误页面而非灰屏
            if (kReleaseMode) ErrorWidget.builder = (details) => MyErrorPage();
        };
        ```
    - 全局未捕获异常 (PlatformDispatcher.instance.onError)：
        - 这是 Dart 3.x 推荐 的最新方式，它能同时捕获同步和异步（Async）的未处理错误，取代了旧版的 runZonedGuarded。

        ```Dart
        PlatformDispatcher.instance.onError = (error, stack) {
            Sentry.captureException(error, stackTrace: stack);
            return true; // 代表异常已被处理，不再向上抛出
        };
        ```

    - 2. Native 侧崩溃：底层信号监听
        - Native 侧（Java/Kotlin, ObjC/Swift）的崩溃会导致 App 直接闪退。这类异常通常是由 JNI 调用出错、内存溢出（OOM）或原生插件 Bug 引起的。
        - 捕获机制：
            - Android：通过 Thread.UncaughtExceptionHandler 捕获 Java 异常，通过 Breakpad 等工具监听 C++ 层的信号（Signal）。
            - iOS：通过 NSSetUncaughtExceptionHandler 捕获异常，通过 Mach 异常处理机制监听底层崩溃。
            - 上报方案：
                - 这是 Sentry 和 Firebase Crashlytics 的核心价值所在。它们会在原生层自动注入 SDK，在 App 下次启动时，将上次闪退的二进制日志（Minidump）上报。

    - 3. 符号化（Symbolication）：还原案发现场
        - 在 Release 模式下，代码经过混淆和 AOT 编译，上报的堆栈全是内存地址（如 0x0000000104764000）。
            - Dart 侧：打包时生成的 debug-info 文件。
            - Android 侧：mapping.txt 文件。
            - iOS 侧：dSYM 文件。
            - 资深做法：将这些符号表文件自动集成到 CI/CD 流水线中。每次 Jenkins/GitHub Actions 打包完成后，自动将符号表上传到 Sentry 服务器，实现堆栈的自动还原。

- 热重载原理：Hot Reload 是如何将增量代码注入 Dart VM 而不丢失状态的？
    - 第一步：开发机 (Host) 的增量编译与补丁生成
        - 当你修改了代码并按下 Cmd+S 或点击闪电图标时，电脑上的 Flutter 工具链开始工作：
        - AST 差异比对：编译器会扫描你的 Dart 源文件，找出自上次编译以来被修改的部分。
        - 生成内核文件 (Kernel / .dill)：它不会重新编译整个 App，而是仅仅把修改过的文件编译成一种平台无关的中间字节码格式（Dart Kernel AST）。
        - VM Service 传输：电脑通过内部的 WebSocket 连接（VM Service），将这个微小的增量 .dill 补丁文件发送到正在运行着 App 的手机或模拟器上。

    - 第二步：Dart VM (Device) 的类替换（保状态的核心所在）
        - 手机上的 Dart VM 收到这个补丁文件后，开始施展真正的魔法。为什么状态不会丢？
        - 代码与数据的物理隔离：在 Dart VM 的堆内存中，“方法/指令（Code）” 和 “实例状态（Data/Heap Objects）” 是分开放的。
        - 指针重定向：当你修改了 build() 方法内部的 UI 逻辑时，VM 会加载新的代码，然后将类的函数指针从旧的代码块指向新的代码块。
        - 状态的免死金牌：在这个过程中，VM 绝对不会去触碰或销毁那些已经在堆内存里分配好的对象实例（比如你的 State 对象、里面的 count 变量、网络请求缓存等）。因为类的方法更新了，但实例的内存布局没变。

    - 第三步：Flutter 框架的重组树 (Reassemble)
        - VM 偷梁换柱完成后，代码是最新的了，但此时屏幕上的 UI 还没变。因为代码还没被执行。
        - VM 会通过内部通道向 Flutter 框架发送一个特定的系统级信号。
        - Flutter 引擎收到信号，触发全局的 reassemble() 生命周期钩子。
            - 这个钩子会遍历整棵 Element 树，将所有的 Element 标记为 dirty（脏节点）。
        - 紧接着，触发下一帧的屏幕刷新（Frame Schedule）。所有的 StatefulWidget 重新执行 build() 方法。
        - 奇迹发生：因为 build() 的代码指针已经被 VM 换成了最新版本，所以它执行了新代码；但同时，它访问的依然是堆内存里那个没被销毁的、带有旧数据的 State 实例！于是，你看到了变色的按钮，并且按钮上的数字依然是之前点击的 5。

- 动画性能：ImplicitAnimations vs ExplicitAnimations，如何选择以获得最高 120Hz 帧率
    - 1. 隐式动画 (Implicit Animations)：甜美的毒药
        - 代表组件：AnimatedContainer, AnimatedPadding, TweenAnimationBuilder 等。
        - 运作原理：当你通过 setState 改变了一个属性（比如 width 从 100 变成 200），框架会自动在内部创建一个 AnimationController，并在指定的时间内为你插值补间。

        - 致命陷阱（为什么会掉帧？）：
            - 隐式动画极易引发布局抖动 (Layout Churn)。假设你用 AnimatedContainer 动态改变高度，每一帧（每秒 120 次），- Flutter 引擎都要被迫执行：
                - 重新 Build -> 重新计算 Layout (因为高度变了，父组件和兄弟组件全受牵连) -> 重新 Paint。
                - 如果里面包裹了一个复杂的列表，CPU 会瞬间被榨干，帧率直接跌破 60。
        - 适用场景：只适用于极其简单的、没有复杂子节点的独立 UI 元素切换。

    - 2. 显式动画 (Explicit Animations)：高帧率的基石
        - 代表组件：AnimationController 配合 AnimatedBuilder，或各种 FooTransition（如 SlideTransition, ScaleTransition）。
        - 运作原理：开发者手动控制动画的生命周期（forward, reverse）。
        - 120Hz 的秘密：child 缓存隔离：
        - 这是显式动画最强大的武器。在使用 AnimatedBuilder 时，你可以将极其复杂的 UI 树通过 child 参数传进去：

        ```Dart
        AnimatedBuilder(
            animation: _controller,
            child: const ExtremelyHeavyWidgetTree(), // ⚠️ 只 Build 一次！
            builder: (context, child) {
                return Transform.translate(
                offset: Offset(_animation.value, 0),
                child: child, // 每一帧复用这个 child，不触发它的 Build 和 Layout！
                );
            },
        )
        ```
        - 每一帧，只有 builder 闭包内的代码会重新执行，那棵庞大的 Widget 树被完美复用，CPU 负担骤降。

    - 3. 终极神技：xxxTransition 与合成器动画 (GPU 硬件加速)
        - 如果想挑战最极致的 120Hz，连 Paint 阶段都应该跳过。
        - Flutter 提供了专门的“过渡组件”（如 SlideTransition, ScaleTransition, RotationTransition, FadeTransition）。
        - 降维打击：这些组件在底层极其特殊。当你使用它们时，Flutter 会为它们创建一个独立的 Layer（图层）。
        - GPU 狂欢：在动画执行时，Flutter 不 Build，不 Layout，甚至不 Paint。它直接把这块已经画好的图层扔给底层的 Skia/Impeller 渲染引擎，告诉 GPU：“我改了矩阵变换参数（Matrix4），你直接在显存里帮我把它平移/缩放一下。”
        - 结果是：CPU 耗时几乎为 0ms，轻松跑满 120Hz。



- 请你在项目中是如何实现动态主题切换的

1. 设计初衷与架构选型 (展现架构思维)
“在做这个功能之前，我首先分析了我们的工程结构。考虑到我们使用的是一种 Workspace / 模块化的架构，其中 lt_uicomponent 被设计为一个基础的核心 UI 库。 为了保持基础组件库的‘纯洁性’和‘高复用性’，我主动放弃了引入 Provider、Riverpod 这种偏业务的第三方状态管理插件，而是选择了完全基于 Flutter 原生的 InheritedNotifier 配合 ChangeNotifier 来从零构建这套主题分发系统。这样不但减轻了包的体积，还使得宿主应用不受限于任何技术栈就能随时接入。”

2. 核心运转机制 (展现基本功)
“在具体实现上，我将系统拆分成了三块：模型层、控制层和供给层。

首先是定义枚举与色彩映射：我抽离出了 LtThemeType 的各种主题枚举（如宇宙主题、自然主题等），并封装了 AppTheme 工厂统一输出 ThemeData。
其次是状态核心：我编写了一整个全局的单例调度器 LtThemeController (继承自 ChangeNotifier)，内部维护着当前的 ThemeType 和深浅模式（ThemeMode）。
最后也是最关键的分发与侦听：我在 MaterialApp 外面包裹了一层自己手写的 LtThemeBuilder 和 LtThemeProvider（基于 InheritedNotifier）。当用户点击切换主题时，Controller 数据一变就会抛出通知，Provider 精准地对依赖它的节点发起 O(1) 复杂度的重绘，生成全新的 ThemeData 给 Material 引擎消费，实现了毫无颗粒感的丝滑瞬切。”
3. 用户体验的兜底与持久化 (展现细节把控)
“仅仅能切换还不够，我还处理了用户的冷启动体验一致性问题。 当用户杀掉 App 并重新大退进入时，肯定希望保留上次的选择。我把 SharedPreferences 的读取融入了 Controller 的初始化生命周期里。 为了坚决不阻塞 Flutter 的主隔离区导致白屏卡顿，我采取了异步非阻塞读取和静默回刷策略：在首次进入渲染时先用默认主题起底，一旦后台毫秒级地读出了磁盘上上一次缓存的主题标识，立刻内存替换并发送重绘信号通知 UI 刷新，达到了接近原生的无缝视觉体验。而在用户每次触发切换皮肤的手指按下之时，除了第一帧渲染给用户看，后台也会静默发出 await prefs.setString 来存盘，真正做到了 UI 线程和 I/O 线程的安全剥离。”
